## 1. 무엇을 읽고 무엇을 읽지 않는가

| 읽는 것 | 신호 | 왜 믿을 수 있나 |
|---|---|---|
| 유닛 유무 | 머리 위 **초록 체력바** | 아군 = 초록 고정. 적은 빨강, 내 전략가는 주황이라 섞이지 않는다 |
| 성급 | 체력바 왼쪽 **배지**(1성 청동 꺾쇠 / 2성 은색 마름모) | 2D 스프라이트. 캡처 7장 102개 배지의 픽셀 색이 **완전히 동일**했다 |
| 장착 아이템 | 체력바 아래 아이콘 0~3개 | 아이템 벤치와 같은 평면 아이콘 → 기존 템플릿 222장으로 매칭 |
| 아이템 **개수** | 아이콘 칸 경계선 | 아이콘을 못 알아봐도 "3개 낀 유닛"이라는 사실은 남긴다 |
| 자리(칸=열) | 체력바 x | 오차 ±25px, 칸 간격 118~128px → 사실상 확실 |
| 자리(줄=행) | 체력바 y | **추정값**(체력바 높이가 챔피언 키에 따라 69~133px). 육각 격자의 반 칸 어긋남 덕에 홀짝은 x로 갈린다(§2.3) |

**챔피언 정체는 읽지 않는다.** 3D 모델은 각도·애니메이션·스킨·성급마다 그림이 달라서, 챔피언별 학습 데이터를
사용자가 만들어야 하는 방식이 된다. 그건 하지 않기로 했다.
2D로 구별할 수 있는 단서(특성 아이콘·코스트 테두리)도 찾아봤지만 **준비 화면의 내 보드에는 그려지지 않는다**
(상점 카드에만 있다) → 낮은 신뢰도 힌트로도 낼 것이 없어 넣지 않았다. 대신 §6의 병합으로 해결한다.

## 2. 기하 (1080p 실측)

### 2.1 체력바와 그 부속 (모두 `vision/board.py` 상수, **프레임 높이 비**로 저장)

```
        배지 ┌──────────────────────────┐ ← 짙은 남색 테두리 2px
        ◀|   │ 초록 64 x 4 px (만피)     │
             ├────┬────┬────┐            ← 바 왼쪽 끝 -6px 에서 시작
             │ 25 │ 25 │ 25 │  아이템 칸 (아이콘 23px)
             └────┴────┴────┘
```

- 체력바: 초록 `HSV H 40~85, S>=100, V>=80`, 만피 64px, 높이 4px. **피가 깎여도 왼쪽 끝은 그대로**라 유닛 중심은
  `왼쪽 끝 + 32`로 계산한다.
- 성급 배지: 바 왼쪽 `-23 ~ -1px`, 세로 `-7 ~ +13px`.
- 아이템 칸: 바 왼쪽 `-6px`부터 25px 간격, 세로 `+10 ~ +35px`. 칸 경계선은 세로 1px 짙은 선이다.

### 2.2 보드 육각칸 28개 · 벤치 9칸 (`vision/regions.py`)

준비 단계 카메라는 고정이라 화면 좌표가 늘 같다. "하나 선택"(모루) 캡처에서 **보라색으로 빛나는 육각칸 9개**를
재서 원근 격자에 맞췄다(칸 중심 오차 <= 10px).

| 줄(행) | 중심 y | 옆 칸 간격 | 칸 0 x | 칸 6 x |
|---|---|---|---|---|
| 0 (내 쪽 맨 앞) | 446 | 118 | 555 | 1263 |
| 1 | 516 | 121.4 | 602 | 1331 |
| 2 | 592 | 125 | 528 | 1278 |
| 3 (벤치 쪽) | 671 | 128 | 580 | 1348 |

- 육각 격자라 **홀수 줄이 반 칸 어긋난다**. 모델은 `x = X0(줄) + 간격(줄) x (칸 - 3 + (줄이 홀수면 0.5))`,
  `X0 = 900 + 3 x (3 - 줄)`. 줄 안에서 오른쪽으로 갈수록 y가 `-0.02 px/px` 올라간다(보드가 살짝 기울어 있다).
- 벤치: 칸 중심 x = `416 + 121 x i`(i=0~8), 체력바가 그려지는 평균 y = 705.
- 보드 가운데 x가 화면 중앙(960)이 아니라 **900**인 것은 오른쪽 플레이어 목록 패널 때문이다. 벤치 중앙도 900으로 같다.

### 2.3 체력바 높이(`BAR_RISE`) — 줄 추정의 한계

체력바는 칸 중심보다 **평균 102px 위**에 그려진다(1080p). 그런데 챔피언 모델 키에 따라 **69~133px**로 달라진다
(표준편차 약 16px). 줄 간격이 70~79px이므로,

- **칸(열)은 확실하다**: 관측 오차 ±25px vs 간격 118~128px.
- **줄(행)은 추정이다.** 다만 생각보다 나쁘지 않다 — **육각 격자의 반 칸 어긋남이 도와준다**.
  홀수 줄이 반 칸(약 62px) 밀려 있어서 **줄의 홀짝은 x만으로 갈린다**(가로 허용 오차 55px보다 크다).
  그래서 y가 실제로 갈라야 하는 것은 이웃 줄(70~79px 차)이 아니라 **같은 홀짝의 줄(146~155px 차)** 이다.
  체력바 높이 표준편차가 16px이므로 4σ 이상 벗어나야 틀린다.
- 그래도 확신할 수 없는 칸은 `UnitSlot.row_unsure=True`로 표시한다(캡처 표본 54칸 중 2칸).

그래도 §6 병합 계약에서 **자리는 참고값**으로 둔다. advisor가 실제로 쓰는 것은 유닛 수·성급·아이템이다.

### 2.4 화면 비율

16:9는 위 실측값, 16:10은 기존 `derive_profile` 규칙(CENTER 기준으로 가로만 `k = 1.778/1.6`배)으로 유도한다.
16:10 실캡처 6장에서 **유닛 수·성급·아이템은 맞지만 줄·칸은 미검증**이다(육각칸이 보이는 16:10 캡처가 없다).
실제로 16:10 캡처 1장에서 유닛 1기가 격자 허용 범위를 벗어나 `hex=None`으로 나왔다 — 그래도 성급·아이템은 남는다.

## 3. 장착 아이템 인식

- 템플릿은 기존 `data/templates/18/items`(212장) + `items_screen`을 그대로 쓴다. 새로 받을 것은 없었다.
- 아이템 벤치 칸(45px)보다 장착 아이콘(25px)이 작아 **템플릿 정규화 크기를 32/38 → 28/34로 바꿔야** 점수가 올라갔다
  (같은 아이콘 0.48 → 0.69). `IconMatcher(size=, search=)`로 크기를 바꿀 수 있게 하고, 상점용 매처를
  `rescaled()`로 다시 정규화해서 쓴다(디스크를 다시 읽지 않는다).
- **임계값**: 점수 >= 0.62, 1위-2위 차 >= 0.12. 캡처의 장착 아이콘 **38칸 실측**에서 맞는 답이 0.664~0.948,
  같은 칸의 2위(다른 아이템)는 0.52 이하였다. 38칸 전부 눈으로 원본 아이콘과 대조해 맞는 것을 확인했다.
- 못 알아본 칸은 **목록에서 빼되 개수(`item_count`)는 남긴다.** `item_count > len(items)`면 "아이템은 꼈는데
  뭔지 모른다"는 뜻이다. 현재 19장에서 못 알아본 칸은 16:10 전투 캡처의 1칸뿐이다(19장 합계 39칸 중 38칸 성공).

## 4. 성급 인식

배지는 2D 스프라이트라 **캡처가 달라도 픽셀 색이 완전히 같다**(서로 다른 캡처·배경의 배지 크롭을 겹쳐 보니
배지 안쪽 픽셀이 한 값도 다르지 않았다). 그래서 학습도 템플릿 파일도 없이 **정확한 색 팔레트 개수**로 가른다.

- 테두리 색 `(35,18,2)` 개수로 "배지가 있다"를 판정한다(초록 유닛 모델·특성 이펙트가 만든 가짜 가로줄을 여기서 거른다).
- 1성 팔레트(청동 15색) vs 2성 팔레트(은색 20색) 중 많은 쪽. 1위가 2위의 2배 이상이어야 한다.
- **3성(금색) 배지는 표본이 없다.** 팔레트를 지어내지 않고 `star=None`을 낸다 → 장부의 성급이 쓰인다(§6 규칙).
  3성 유닛이 있는 캡처 1장이면 팔레트를 뽑아 바로 넣을 수 있다.

## 6. app 병합 계약 (구매 추적 담당자가 코딩할 대상)

vision은 **자리·성급·아이템**을, app 장부는 **정체**를 안다. 둘을 합쳐 `GameState.board`/`bench`를 만든다.

### 6.1 vision이 내놓는 것

```python
rec = Recognizer(...)
state = rec.recognize(frame, groups={..., "board"})   # "board"는 DEFAULT_GROUPS에 포함
read  = rec.last_board_read        # vision.board.BoardRead | None
```

- `recognize()`는 `GameState.board`/`bench`를 **채우지 않는다**(정체를 모르니까). 대신 `last_board_read`에 넣는다.
- `board` 묶음을 읽지 않았거나 화면이 준비/선택 화면이 아니면 `last_board_read is None`이다.
  **None은 "보드가 비었다"가 아니라 "이번 프레임에서 안 읽었다"** 이다 → 직전 값을 유지해야 한다.
- 매 `recognize()` 시작에 None으로 초기화된다(낡은 값이 남지 않는다).

```python
@dataclass(frozen=True)
class BoardRead:
    board: tuple[UnitSlot, ...]    # 보드 칸(유닛이 있는 칸만)
    bench: tuple[UnitSlot, ...]    # 벤치 칸(유닛이 있는 칸만)
    confidence: float              # 칸 신뢰도 최솟값
    bars: int                      # 찾은 체력바 수 = len(board) + len(bench)
    unresolved_items: int          # 아이콘은 있는데 못 알아본 칸 수
    def all_item_ids(self) -> list[str]: ...

@dataclass(frozen=True)
class UnitSlot:
    star: int | None               # 1 | 2 | None(모름 — 3성 배지 미수집 포함). **3은 아직 나오지 않는다**
    items: tuple[str, ...]         # 알아본 장착 아이템 **대표 ID**(0~3개)
    hex: tuple[int, int] | None    # (줄 0~3, 칸 0~6). 줄 0 = 내 쪽 맨 앞, 칸 0 = 왼쪽. 보드 칸만
    bench_slot: int | None         # 0~8. 벤치 칸만
    confidence: float              # 0.85(자리 확정) | 0.6(자리 미상)
    unit_id: None                  # **언제나 None.** vision은 챔피언을 식별하지 않는다
    item_count: int                # 화면에 붙어 있던 아이템 칸 수 0~3
    item_conf: float               # 아이템 매칭 최소 점수
    star_conf: float               # 0.92(판독) | 0.0(모름)
    row_unsure: bool               # 줄(행)이 애매했다. 칸(열)은 영향 없음
    anchor: tuple[float, float]    # 체력바 가운데의 비율 좌표. 프레임 사이 같은 유닛을 잇는 데 쓸 수 있다
```

### 6.2 합치는 규칙 (app 쪽 `unit_merge.merge_units`가 이미 이대로 구현되어 있다)

| 값 | 누가 이기나 | 이유 |
|---|---|---|
| 유닛 **수** | **vision** | 화면에 보이는 것이 사실이다. 장부가 더 적으면 남는 칸은 `UNKNOWN_UNIT_ID` |
| **성급** | **vision** (단 `None`이면 장부) | 배지를 직접 읽었다. 3성은 아직 None이라 자연히 장부가 채운다 |
| **장착 아이템** | **vision** | 직접 읽었다. `item_count > len(items)`면 "못 알아본 칸이 있다" |
| **자리**(hex/bench_slot) | **vision** | 장부는 자리를 모른다. 단 **줄은 추정값**이다(§2.3) |
| **정체**(champion_id) | **app 장부** | vision은 항상 None |

app이 붙이면 되는 것:

```python
from tft_advisor.app.unit_merge import board_obs_from, merge_units
obs = board_obs_from(rec.last_board_read)      # BoardRead → BoardObs (그대로 들어간다)
result = merge_units(ledger, obs, level=state.level)
```

`tests/test_vision_board.py::test_board_read_matches_app_unit_merge_contract`가 이 연결을 고정한다
(`isinstance(read, app.unit_merge.BoardRead)` / `isinstance(slot, UnitSlotRead)` / `board_obs_from(read)` 왕복).

### 6.3 정체 없이도 지금 당장 쓸 수 있는 것

`items_ready`(보유 완성템)는 **정체를 몰라도** 개선된다. `BoardRead.all_item_ids()`가 보드+벤치 장착분을
그대로 주므로, 아이템 벤치(미장착) + 장착분 = 보유 아이템 다중집합이 화면에서 직접 나온다.
지금까지는 세션 추적 추정값(`equipped_tracked`)뿐이었다.

## 7. 비용

1080p 캡처(보드 9기 + 벤치 9기 = 18기, 장착 아이콘 9칸), 맥 `.venv` python 3.14 기준:

| 항목 | ms/프레임 |
|---|---|
| `board_reader.read` 전체 | **80** |
| ├ 체력바 찾기(보드+벤치 영역) | 13 |
| ├ 성급 배지 18개 | 16 |
| └ 장착 아이콘 9칸 매칭 | 48 |
| `recognize()`에 `"board"`를 더해 늘어난 시간 | **약 87** (1691 → 1778) |
| `recognize(DEFAULT_GROUPS)` 전체 | 약 1.8 s (대부분 OCR) |
| `change.roi_signatures` 전체 묶음(보드 포함) | 3.2 |

즉 **묶음 하나가 한 프레임의 5% 정도**다. 유닛이 적으면 더 싸다(유닛 수에 비례한다).

- **묶음으로 빼고 넣을 수 있다**: `recognize(groups=...)`에서 `"board"`를 빼면 비용이 0이다.
  `change.roi_groups`에도 `"board"`가 있어서 **보드/벤치 영역이 바뀐 프레임에서만** 다시 읽는다.
- 읽는 화면은 `READ_MODES["board"] = {PLANNING, ITEM_SELECT}`뿐이다. 전투 중에는 유닛이 칸을 떠나 자리가
  뜻이 없고, 캐러셀·증강 화면에는 보드가 없다.
- 덤: `IconMatcher.match`를 템플릿마다 `cv2.matchTemplate`을 부르는 대신 **행렬곱 한 번**으로 바꿨다.
  222장 기준 43 ms → 6.5 ms(7배). 값은 OpenCV `TM_CCOEFF_NORMED`와 같다(오차 2e-5 이하, 테스트로 고정).
  **아이템 벤치 10칸 인식도 같이 빨라져** 전체 프레임 시간이 크게 줄었다(측정 환경 부하 때문에 절대값은 참고만).

## 8. 밀려 있던 화면 상태 오류 2건

### 8.1 16:10 1-3 — 내 예전 초안 라벨이 틀렸다

예전 초안은 `screen_mode: combat`이었는데 **준비 단계가 맞다.** 라벨을 고쳤고 그 이유를 파일에 적었다.
새 캡처 쌍(`전투 전`/`전투 시작` 4쌍)으로 확인한 두 신호가 모두 준비를 가리킨다.

- 보드 가운데 `N/M` 워터마크가 보인다(전투가 시작되면 사라진다).
- **벤치 유닛의 체력바가 보인다**(전투 중에는 사라진다) ← 이번에 새로 찾은 신호.
- PvE 라운드는 **준비 단계에도** 크립이 빨간 체력바를 달고 서 있으므로 빨간 바는 전투의 증거가 아니다.

### 8.2 16:10 3-7 원정 전투 — UNKNOWN → COMBAT

상대 아레나에서 전투를 보는 화면은 하단 상점 HUD가 없어 예전에는 UNKNOWN(안전 실패)이었다.
규칙을 하나 더했다: **상점 HUD가 없고, 스테이지가 읽히고, 라운드가 캐러셀(4)이 아니고, 적 체력바가 2개 이상**이면
COMBAT(신뢰도 0.7). 캐러셀에는 체력바가 없어 섞이지 않는다.

### 8.3 새 신호: 벤치 체력바 = 준비 확정

`ModeSignals.bench_bars`를 더했다. **전투가 시작되면 벤치 유닛의 체력바가 사라진다**
(준비 7장 4~9개 / 전투 5장 모두 0개). 워터마크가 유닛에 가려 안 읽힐 때 준비를 확정하는 **한 방향 신호**다
(있으면 준비, 없으면 모름).
반대 방향(없으면 전투)으로는 쓰지 않았다 — 벤치가 빈 준비 화면(1-1 등)을 전투로 오판하면 추천이 멈춘다.

**결과: 원본 캡처 19장 screen_mode 19/19.**
