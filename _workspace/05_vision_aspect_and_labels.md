## 3. 비율 규칙 (핵심 발견)

16:9 fixture(2001x1126)와 16:10 캡처(1273x795)에서 같은 UI 요소의 OCR 박스 위치를 비교해서 얻었다.

**TFT HUD는 화면 높이에 비례해 커진다.** 그래서 세로 비율 좌표는 비율이 달라져도 그대로이고, 가로 비율 좌표만 바뀐다.
요소마다 가로 기준점이 다르다:

| 기준점 | 요소 | 사상식 (k = 기준비율 ÷ 대상비율) | 검증 |
|---|---|---|---|
| **CENTER** | 상단 스테이지 막대·라운드 아이콘, 하단 HUD 전체(레벨·XP·확률·골드·연승·버튼·상점 5칸·가격), 증강 카드 3장 | `x' = 0.5 + (x − 0.5)·k` | "경험치 구매" 예측 0.1536 / 실측 0.1537~0.1555. 상점 0번 칸 예측 0.2649 / 실측 0.2667~0.2679. 골드 예측 0.5319 / 실측 0.5365. 증강 카드 중심 예측 0.2621·0.7368 / 실측 0.266·0.739 |
| **LEFT** | 왼쪽 세로 아이템 벤치, 특성 패널 | `x' = x·k` | 특성 이름 예측 0.0784 / 실측 0.0786. 인원수 숫자 예측 0.0671 / 실측 0.0668 |
| **RIGHT** | 오른쪽 플레이어 목록 | `x' = 1 − (1 − x)·k` | 대략 맞으나 ±0.01 어긋남(기준이 방송 크롭이라 오른쪽 가장자리 신뢰도가 낮다) → 실측으로 덮어씀 |

16:9(1.7778) → 16:10(1.600)이면 k = 1.111이다. 즉 **HUD가 화면 가로의 더 큰 비율을 차지하고, 중앙을 기준으로 벌어진다.**

`src/tft_advisor/vision/regions.py`에 넣었다.

```python
class Anchor(StrEnum): CENTER / LEFT / RIGHT
ANCHORS: dict[str, Anchor]                      # Profile 필드 18개 전부에 지정(테스트로 고정)
derive_profile(ref, name, aspect, *, ref_aspect=16/9, dy, dy_fields, overrides) -> Profile
```

### 세로 보정 `BOTTOM_HUD_DY = 0.006`

하단 HUD만 16:9 기준값보다 0.006(약 5px@800p) 아래에 있다. 상단 막대·특성 패널·플레이어 목록·증강 제목은 세로가 정확히 일치한다.
원인은 **기준(16:9) fixture가 방송 크롭이라 게임 화면보다 아래로 약 8px 길기 때문**으로 보인다(하단 앵커 요소만 위로 밀린다).
→ 유도 프로파일에서는 하단 HUD ROI 11개에만 `+0.006`을 준다. **16:9 프로파일 자체는 건드리지 않았다**(그 값은 그 크롭에 대해서는 맞고, 바꾸면 기존 회귀 기준선이 깨진다). 원본 1920x1080 캡처가 오면 기준값을 고치고 이 보정을 없앤다.

## 4. 화면 크기 설정 (사용자 요청 "앱에 화면 크기 옵션")

`config/settings.toml` `[vision]`에 4개를 추가했다. **전부 기본값이 자동**이라 아무것도 안 건드려도 동작한다.

| 키 | 기본값 | 뜻 | 검증 |
|---|---|---|---|
| `resolution` | `"auto"` | 게임 해상도. `"1280x800"`처럼 적으면 그 비율로 ROI를 고른다 | 정규식 `^(auto\|\d{3,5}x\d{3,5})$` |
| `aspect` | `"auto"` | ROI 배치 비율. `"16:9"` \| `"16:10"` \| `"4:3"` \| `"21:9"` \| `"32:9"` | Literal. `resolution`과 어긋나면 **설정 오류**(3.5% 허용 오차) |
| `profile` | `"auto"` (전 `"1920x1080"`) | 고급. ROI 프로파일 이름을 못박는다 | `Recognizer`가 해석, 없는 이름이면 KeyError |
| `content_box_auto` | `true` | `content_box`가 없을 때 레터박스(검은 띠)를 자동으로 잘라낸다 | |
| `content_box` | (없음) | 기존 키. 프레임 안 게임 화면 영역 비율 | 기존 그대로 |
| `ocr_backend` 등 | | 기존 키 전부 그대로 | |

**우선순위** (`VisionCfg.aspect_setting()`): `profile` > `aspect` > `resolution` > `"auto"`(프레임에서 자동 판별).
`Recognizer(profile=…)` 인자를 직접 주면 그것이 최우선이다(테스트·디버그용).

**게임 화면 영역 우선순위** (`Recognizer.content_for()`): `recognize(content=…)` 인자 > 설정 `content_box` > (`content_box_auto`면) 레터박스 자동 탐지 > 프레임 전체.

**중요**: ROI 프로파일은 프레임이 아니라 **content_box를 적용한 뒤의 게임 화면 영역 비율**로 고른다. 1920x1200 화면에 16:9 게임이 레터박스로 떠 있으면 16:9 프로파일이 선택된다.

### 자동 판별 동작

- `profile_for_frame(w, h)` → `aspect_name(w/h)` → 가장 가까운 지원 비율(상대오차 ≤ 3.5%) → 실측 프로파일 or 유도.
- 실제 캡처 6장(1.5885~1.6048)과 기존 fixture 7장(1.7748~1.7896)이 전부 올바르게 판별된다(테스트로 고정).
- `detect_content_box()`는 **검은 띠만** 잘라낸다(줄 평균 ≤ 12, 최댓값 ≤ 44, 8px 이상, 한 방향 25% 이하). 창모드로 바탕화면이 함께 찍히는 경우는 검은 띠가 아니므로 탐지하지 않는다 → `content_box`를 직접 지정하거나 `MssSource(region=…)`로 창만 캡처한다(문서화).

### Recognizer 구조 변경

`self.profile`(고정 1개)이던 것을 **프레임마다 고르는 방식**으로 바꿨다. `recognize()`가 `P = self.profile_for(box_w, box_h)`를 구해 각 `_read_*` 헬퍼에 인자로 넘긴다. `Recognizer.profile` 속성은 프레임 크기를 모르는 호출자(`change.ChangeDetector`, `templates debug-rois`)를 위해 남겼다.
`templates.py`의 `--profile` 기본값도 `auto`로 바꿨다(16:10 캡처에서 harvest/debug-rois가 바로 동작한다).

### 6-2. `_read_traits`가 다른 행의 숫자를 인원수로 붙였다

16:10 캡처에서 `("약탈자", 8)`, `("악의 여단", 12)` 같은 **확신에 찬 오답**이 나왔다(구간 사다리 "2>4>6"의 숫자를 위/아래 행의 인원수로 착각). 두 가지 가드를 넣었다.
- 인원수 숫자는 이름 **바로 왼쪽**(글자 높이 1.5배 이내)에 있어야 한다.
- 인원수가 `max(breakpoints) + 2`를 넘으면 버린다.

`active_traits`는 여전히 기본 묶음에서 제외이고 신뢰도가 임계 미만이라 advisor가 쓰지 않는다(진단용).

### 6-3. items 미인식 1건의 진짜 원인

`unnamed-5`의 items가 None인 것은 **아이콘 매칭 실패가 아니다**. 5칸 전부 1.0으로 맞는다. 이 화면이 `screen_mode = unknown`이라 `_read_items`가 아예 호출되지 않기 때문이다. **화면 상태 규칙 1개가 없어서 items까지 못 읽는 구조**다.

### 준비/전투 구별에 쓸 수 있어 보이는 신호 (측정해 둠, 이번엔 넣지 않음)

- **"준비" 배너**: 준비 캡처 2장 모두 화면 가운데 위에 "준비" 글자가 있다. 위치(16:10) x 0.4832~0.5212, y 0.1351~0.1740 → 16:9 환산 약 `Rect(0.455, 0.125, 0.545, 0.185)`. `augment_title` ROI(y 0.18~0.24)와 겹치지 않는다.
  **한 방향으로만 안전한 신호**다: 보이면 확실히 준비, 안 보이면 모름. 다만 **라운드 시작 순간에만 뜨는 배너**라 준비 단계 중간 프레임에는 없다. 그래서 단독으로는 부족하다.
- **상대 이름표**: 전투 캡처 2장(자기 보드 4-5, 상대 보드 3-7)에 화면 위쪽 상대 닉네임 + 레벨 표시가 있다. 위치가 장마다 달라 ROI가 넓어야 하고, PvE 전투(1-3)에는 없다.
- **보드 위 빨간 체력바(적 유닛)**: 전투 3장에 있고 준비 2장에 없다. 픽셀 신호로 만들 수 있으나 표본이 한 판 5장뿐이라 넣지 않았다.

→ 셋 다 **표본 부족**이다. 같은 라운드의 준비/전투 쌍이 오면 세 신호를 한꺼번에 검증해서 넣겠다. 그 전까지 `planning`은 문서대로 "준비 또는 전투"를 뜻한다(advisor 동작에 해는 없다 — 전투 중에도 상점 구매는 가능하다).
